One stack, built bottom‑up

Each layer unblocked the one above it. The models are trained on the framework; the framework trains on data the pipeline engine produced; the engine reads through the storage layer; and all of it runs on the cluster tooling at the bottom.

  1. Models

    Patram 1.5 and DocLayout‑VL

    Patram 1.5 is BharatGen's document vision‑language model, now training a 7B model on 128 GPUs, with a 41.3‑billion‑token corpus, a task taxonomy I designed and question‑answer data I generated. DocLayout‑VL reads a page and writes out its layout as a tree, grounding every node as a pixel mask, steered by natural‑language prompts; accepted to ECCV 2026.

    79.4 vs 45.8DocLayout‑VL on HOPLay‑Docs‑Bench against the best fine‑tuned baseline
  2. Training

    Training framework

    The framework both models above are trained on. Models, datasets, dataloaders and evaluation are registered independently, so a new combination is a config change rather than new code. Non‑compute tensors stay on the CPU so GPU memory holds only what the model computes on, and multi‑node training runs over AWS EFA at close to the interconnect's ceiling.

    97.8%of single‑node all‑reduce bandwidth retained across two nodes
  3. Pipelines

    Patram‑Ingest

    The engine that generated the training data for the models above. A pipeline is declared as a graph of stages that fan out, merge, and route individual items down different paths at runtime; every stage runs concurrently, so the pipeline moves at the speed of its slowest stage rather than the sum of all of them. Any machine can die mid‑run and the run resumes where it left off, with nothing lost and nothing processed twice.

    8.47M promptsone run, scaled 5 → 24 nodes (192 GPUs) unattended, 99.977% completed
  4. Storage

    Patram‑FS

    Datasets are packed into a few hundred large shards for the storage layer, while every sample keeps its own byte address for the training layer. Training runs now read from node‑local NVMe and S3 only, at local‑disk speed, with the shared network filesystem off the data path entirely.

    10M → 200storage requests per training run
  5. Operations

    Cluster‑Supervision

    30 nodes with 240 H100 GPUs, running training, inference and data generation side by side, managed from a single dashboard. A collector on every node reports GPU, node and storage health into Postgres, with GPU readings every 10 seconds aligned to the wall clock so readings from different nodes line up exactly. 41 transition‑based alert rules watch the fleet, and a watcher rebuilds a node that AWS has replaced.

    ~1 minutewatcher cycle that notices a replaced node and rebuilds it into the cluster, no manual step

DocLayout‑VL

Research · ECCV 2026
Problem
Document layout analysis stayed closed‑set while the rest of vision moved to promptable models: a fixed label list, flat boxes, no hierarchy, and retraining as the only way to add a region type.
Built
A VLM that generates the layout as a serialized tree with an anchor token per element; a Hierarchical Grounding Contextualizer that applies attention constrained by the predicted tree; a SAM‑based decoder that turns each anchor into a mask. HOPLay‑Docs‑80M (2.5M pages, 80M masks, 40 languages) and a 5,000‑document benchmark, because no dataset with hierarchy, open‑set labels and prompts existed. Trained on 64 H100s with DeepSpeed ZeRO‑3.
Measured
  • 79.4 overall on HOPLay‑Docs‑Bench, against 45.8 for the best fine‑tuned baseline, 37.2 for Gemini 3 Pro and 28.6 for GPT‑5.2
  • Zero‑shot on ten public layout benchmarks, it matches or beats detectors trained on each one

Patram 1.5

Foundation model · Data and training
Problem
"Make the model good at documents" is not a plan. Without a written specification of what to learn, nobody can say what is missing from a corpus, whether it is done, or what a new dataset adds.
Built
A taxonomy of 186 atomic tasks across 12 capabilities and 86 document properties, with a compatibility matrix whose gates are parsed and checked by a verifier. A deficit‑weighted sampler steers generation toward under‑filled tasks, and every record carries the design version that produced it.
Measured
  • Current training corpus: 50.8M examples and 41.3B tokens across 13 groups of tasks, from OCR and HTML to question answering
  • The first question‑answer corpus generated against the spec matched the designed task mix
  • Now training a 7B document model on 128 GPUs

Patram‑Ingest

Pipelines · Python, PostgreSQL, vLLM
Problem
Building the corpus meant running GPU models over hundreds of millions of images for days on a shared cluster where nodes get reclaimed, servers die and processes get killed. Hand‑written scripts lost or duplicated work on every crash.
Built
A data engine for running GPU models over very large image sets. Pipelines are declared as a graph of stages rather than hand‑coded: stages fan out, merge, and route individual items down different paths at runtime, and every stage runs in parallel with the others so nothing sits idle waiting on the one before it. The same engine scales from one machine to the full fleet, and any machine can die at any moment: the run resumes where it left off with a few minutes of work redone, nothing lost and nothing processed twice. It can also drive vLLM servers that other people run: when a server goes to sleep or restarts, its workers pause and the work goes elsewhere instead of being marked failed.
Measured
  • Largest run: 8.47M prompts through a 27B model, scaled live from 5 to 24 nodes (192 GPUs) unattended, 99.977% completed
  • +29% throughput on identical hardware after removing GPU idle time between batches
  • Later Patram 1.5 data runs drove up to 49 nodes through shared vLLM servers

Patram‑FS

Storage · Go, Python
Problem
A training run over a document dataset touched about ten million small files. Shared filesystem metadata and S3's per‑prefix request‑rate ceiling, not bandwidth, set the pace for 240 GPUs.
Built
Datasets packed into uncompressed TAR and JSONL shards so every sample has a fixed byte address. One Go daemon per node deduplicates downloads to local NVMe and warms the kernel page cache; the daemon stays off the read path, so every worker reads at raw pread speed. Prometheus metrics, fleet deploy tooling and a supervisor loop around it.
Measured
  • ~10M → ~200 storage requests per training run, and annotation reads from 297.6 → 26.7 µs
  • Runs on every node of the cluster; training jobs no longer touch the shared filesystem

Also built

  • Training frameworkTraining · PyTorch, DeepSpeed, Docker, NCCL

    Two fixes took the trainer from one document per GPU to six: non‑compute tensors such as debug‑only page images stay on the CPU instead of being copied into GPU memory, and validation reduces every mask to seven numbers on each rank before anything is gathered. Multi‑node training then needed an EFA container image, an idempotent node‑init script and the right NCCL environment; eight failure modes are documented, including NCCL silently falling back to TCP. This is the stack DocLayout‑VL was trained on and the ancestor of patram‑core, the team's current trainer. Technical write‑up
