Patram 1.5

7B vision‑language model · BharatGen

Launch blogHugging Face

Patram 1.5 is BharatGen's 7B vision‑language foundation model for document understanding. It has the top overall score among the 21 VLMs we benchmarked, level with models up to 97 times its size, and it adds two capabilities: OCR 3.0 (extract exactly what you ask for, in the format you ask for) and abstention (answer "I don't know" instead of guessing).

I worked on it across the whole stack. I built its data programme: a task taxonomy of 186 tasks across 12 capabilities with a machine‑checked compatibility matrix, and question‑answer and OCR data generated through large‑scale teacher distillation on up to 49 nodes, including the data behind OCR 3.0 and abstention. I then trained the model on 128 GPUs with Hugging Face Trainer and DeepSpeed ZeRO, handling multimodal sampling, sequence packing, memory management and distributed validation. Every layer under it is a system I built: the data was generated with Patram‑Ingest, served by Patram‑FS, trained on Patram‑Core and evaluated on Patram‑Eval.

DocLayout‑VL

Layout foundation model

Project page

DocLayout‑VL reframes document layout analysis as open‑set, hierarchical, promptable segmentation. Layout models had been stuck with fixed label sets, flat labels and axis‑aligned boxes. Ours takes a page and a natural‑language prompt: a VLM generates the layout as a tree with open‑vocabulary labels, and a hierarchy‑aware grounding module, using tree‑aware attention over parent, child and sibling nodes, turns every node into a pixel‑accurate mask.

To train it we built HOPLay‑Docs‑80M: 2.5M pages in 40 languages with 80M pixel masks and 400K open‑set labels. On our benchmark it more than doubles the scores of Gemini 3 Pro and GPT‑5.2, and zero‑shot it outperforms both, and matches or beats per‑dataset specialist detectors, across 10 public benchmarks.

Evaluation

Patram‑Eval

Python · PostgreSQL · vLLM

Patram‑Eval is the evaluation system behind every decision on Patram, and where the Patram 1.5 launch comparisons were run. Its leaderboard spans 208 models on 105 benchmarks, from 1B to 3T parameters, and each model and benchmark pair needs its own vLLM serving recipe, prompt, parser and scorer.

I redesigned its execution around one shared work list that every node pulls from, so the whole fleet coordinates itself with no manual scheduling. Benchmarks are cut into chunks that move through generate, parse, score and judge as rows in a single task table. A service on each GPU node claims the tasks that fit its free GPUs and CPU cores, and commits results in the same transaction that closes the task, so a node can die mid‑run and its work goes to another. Results are insert‑only and keyed by input hash, which traces every score to the exact request, model build and scorer version. At peak it ran 1.76M generations in an hour.

Training

Patram‑Core

PyTorch · DeepSpeed ZeRO · Hugging Face · NCCL

Patram‑Core is the team's custom distributed trainer, built on Hugging Face Trainer and DeepSpeed ZeRO‑3, and the framework both models were trained on. The code I started from hard‑wired each training script to one model and one dataset, was pinned to a batch size of 1 per GPU and ran on a single node.

I rebuilt it around a dataset registry and a model registry, so any dataset trains with any model family from one YAML config. To fix memory I pinned non‑compute tensors to CPU and reduced validation metrics per rank before any cross‑GPU gather, which eliminated the OOMs and raised per‑GPU batch size from 1 to 6–8. I then tuned multi‑node communication for AWS EFA, retaining 97.8% of all‑reduce bandwidth across nodes, and added multimodal sampling and sequence packing for the Patram 1.5 runs.

Data generation

Patram‑Ingest

Python · PostgreSQL · vLLM

vLLM Meetup talkIIIT Hyderabad lecture

Patram‑Ingest is a crash‑safe, exactly‑once distributed data engine for GPU inference over 100M+ images, and it generated the Patram 1.5 training data. Jobs run for weeks on a fleet where nodes fail, leave and join, so every item's state is tracked in PostgreSQL: workers claim items under row locks, and results commit in a fixed order that limits what a crash can cost to the last uncommitted batch.

Pipelines are DAGs with fan‑out, fan‑in and per‑item routing decided at runtime, each stage declared in a few lines of config. Moving the GPU stages to continuous batching against vLLM lifted throughput 29% on identical hardware by removing the GPU idling between batches. A restarted node reclaims the items it was holding, and nodes can join or leave mid‑run.

Storage

Patram‑FS

Go · Python · S3 · NVMe

Patram‑FS is a per‑node Go storage daemon that serves multi‑TB datasets from S3 through local NVMe. Before it, a training run opened around ten million small files on the shared filesystem, overloading its metadata service for the whole cluster and leaving GPUs waiting on I/O.

Datasets are packed into about 200 large shards, and every sample is addressed by shard, byte offset and length. The daemon keeps one cache per node shared by every process, collapses concurrent requests for a shard into a single download, and stays off the read path: it returns a local path and offset, and the client reads straight from NVMe. That cut storage requests per run by 50,000×, sped up annotation reads 11× through kernel page‑cache warming, and took the shared filesystem off the training data path. It's now used across the team's training and data pipelines.

Cluster

Cluster‑Supervision

Kubernetes (k3s) · PostgreSQL · Python · JavaScript

Cluster‑Supervision is the control plane for our fleet of 64 nodes and 512 GPUs. It replaced five separate sites and logging into nodes over SSH with one k3s cluster: per‑node collectors run as a DaemonSet, alert rules are SQL evaluated on a schedule, and a FastAPI dashboard reads everything from one PostgreSQL. What it covers:

  • Kubernetes across 64 nodes and 512 GPUs, with a highly available PostgreSQL and a dashboard that runs on three replicas
  • Self‑healing nodes: a machine AWS replaces is noticed and rebuilt into the cluster in about a minute, with no one involved
  • Health every 10 seconds from every node: GPUs, host, storage and S3, with a read‑only SSH probe when a node stops reporting
  • 41 alert rules in three tiers, each with a one‑line runbook
  • GPU usage and booking: who is on which GPU, reservations, and idle bookings released automatically
  • Model hosting: keeps shared vLLM servers alive, and lends their GPUs out by putting a server to sleep
  • Storage explorer for the shared Lustre store and every node's NVMe, kept current without walking the disks
  • Self‑service PostgreSQL databases, one isolated cluster per project
  • Runs the Patram‑FS daemon on every node and tracks Patram‑Ingest runs, with a remote stop
  • S3 browser, and web apps on any node opened through the dashboard without an SSH tunnel
