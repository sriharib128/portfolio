Evaluation

Patram‑Eval

Python · PostgreSQL · vLLM

Every decision on Patram rests on these numbers: what to train next, whether a change helped, whether we are heading in the right direction. So they have to be right, and they have to arrive fast. Patram‑Eval is the system that produces them, and where the comparisons for the Patram 1.5 launch were run.

The hard part is scale. The leaderboard covers 208 models, from 1B up to 3T parameters, the largest served across four nodes, on 105 benchmarks, and every model and benchmark pair needs its own serving setup, prompt, pre‑ and post‑processing and scorer. Getting each of those right, and tuning 200+ serving recipes, was most of the work.

Running it by hand did not scale, so I redesigned it as one system. Every step, from rendering pages to generating, parsing, scoring and judging, is a task in one PostgreSQL work list, and an agent on each GPU node takes whatever fits its free GPUs and CPUs, reaching 1.76M generations in an hour. Benchmarks, parsers and scorers are plugins, results are never overwritten, and every number traces back to the exact request, model build and scorer version.

Storage

Patram‑FS

Go · Python · S3 · NVMe

Training was waiting on the shared filesystem, not the GPUs. Patram‑FS packs datasets into large shards where every sample keeps its byte address, caches them once per node on local NVMe, and lets training read straight from local disk. Patram 1.5 trained this way.

Cluster

Cluster‑Supervision

Kubernetes (k3s) · PostgreSQL · Python · JavaScript

The control room for our GPU fleet: one Kubernetes cluster and one dashboard in place of five single‑machine sites and logging into nodes by hand.

  • Kubernetes across 64 nodes and 512 GPUs, with a highly available PostgreSQL and a dashboard that runs on three replicas
  • Self‑healing nodes: a machine AWS replaces is noticed and rebuilt into the cluster in about a minute, with no one involved
  • Health every 10 seconds from every node: GPUs, host, storage and S3, with a read‑only SSH probe when a node stops reporting
  • 41 alert rules in three tiers, each with a one‑line runbook
  • GPU usage and booking: who is on which GPU, reservations, and idle bookings released automatically
  • Model hosting: keeps shared vLLM servers alive, and lends their GPUs out by putting a server to sleep
  • Storage explorer for the shared Lustre store and every node's NVMe, kept current without walking the disks
  • Self‑service PostgreSQL databases, one isolated cluster per project
  • Runs the Patram‑FS daemon on every node and tracks Patram‑Ingest runs, with a remote stop
  • S3 browser, and web apps on any node opened through the dashboard without an SSH tunnel
